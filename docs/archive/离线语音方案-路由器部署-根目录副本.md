# 离线语音控制方案（路由器部署）

> 架构师：AI架构师 | 日期：2026-06-23 | 更新：2026-07-01
> 目标设备：128MB MIPS架构路由器（可用内存约50MB）

---

## 一、架构选型：为什么是 Linux 原生方案？

核心目标：**不影响路由器网络吞吐**的前提下，实现精准、低延迟的离线语音控制。

### 三套候选架构全景对比

| 评估维度 | 方案 A：外挂 MCU 芯片 | 方案 B：Linux 原生服务（✅ 选中） | 方案 C：端侧大模型 |
|---|---|---|---|
| **系统架构** | 独立外挂芯片 + 裸机/RTOS | 路由器主 SoC 复用 + Linux Daemon | 独立 AI 算力板 + 容器化 |
| **内存消耗** | < 1 MB（高价 SRAM） | **10-50 MB（廉价 DDR）** | > 1-4 GB（LPDDR） |
| **硬件 BOM** | +独立语音芯片 | **+麦克风阵列** | +昂贵边缘计算主板 |
| **交互能力** | 固定命令词（100-300条） | **数百词条 + 复杂状态机** | 自然语言自由理解 |
| **端到端延迟** | < 300 ms | **500-1000 ms** | 2000-5000 ms+ |
| **业务确定性** | 绝对精确 | **绝对精确** | 存在幻觉风险 |
| **开发门槛** | 高（跨技能栈） | **中（标准 Linux）** | 极高 |

### 决策理由

**放弃 A（MCU）：** 路由器主板已有 SoC 和上百兆 DDR，外挂专用语音芯片是硬件上的重复建设；裸机固件与 Linux 主业务通过低速 UART 通信，OTA 升级和状态同步极度繁琐。

**放弃 C（LLM）：** 最小量化版仍需 >1GB 内存，百元路由器成本直冲千元级；5-15W 推理功耗在无主动散热的密闭空间内会导致芯片积热降频；家电控制是强确定性指令映射，LLM 的幻觉是不可接受的。

**选中 B：** 复用现有 DDR 内存（边际成本极低），标准 Linux 生态（ALSA 音频、UBus IPC），cgroups 资源限制保障网络转发优先。用几十兆廉价内存换取零额外芯片成本 + 统一软件栈 + 可控确定性。

> ⚠️ MIPS 单核 580-880MHz 算力瓶颈：ASR 推理可能占用 50-80% CPU。应对：VAD 静音检测 + cgroups CPU 配额；推荐硬件基线 256MB 双核路由器。

## 二、内存预算

### 2.0 双模式部署

| 模式 | 运行环境 | 启动命令 | 用途 |
|------|---------|---------|------|
| **预研 Web** | Mac / 开发机 | `python3 -m voice_router_lite web` | ESP32 联调、控制台演示、ASR 样本采集 |
| **量产 Daemon** | OpenWrt 路由器 | `python3 -m voice_router_lite router --config deploy/openwrt/voice-router.json` | ALSA 直连麦克风、KWS 常驻、ubus 控制 |

预研阶段用 **Mac Web 服务 + ESP32 WebSocket** 验证 NLU/设备逻辑；**烧录路由器时切换为 Daemon 架构**（USB-I2S + KWS，见下图）。

#### 路由器量产架构（推荐）

```
USB-I2S 麦克风
      │
      ▼
   ALSA 采集
      │
      ▼
voice-routerd  (python3 -m voice_router_lite router)
      │
      ├─ 待机: KWS + NLU(INT8) 常驻
      ├─ 唤醒: 卸载 KWS → fork ASR 子进程 → 识别完进程退出
      └─ ubus → OpenWrt 网络/系统/GPIO 控制
```

| 策略 | 作用 |
|------|------|
| `model_serial_exclusive` | KWS / ASR **不同时驻留** DDR |
| `asr_subprocess` | ASR 在**独立子进程**，退出后内核回收全部 ASR 内存 |
| `VOICE_ROUTER_ASR_WORKER` | 可选 C++ 原生 worker（`native/`），峰值再省 ~24MB |
| `prefer_int8_nlu` | NLU 使用 INT8 模型（~3MB 替代 ~11MB） |
| `procd` 托管 | 见 `deploy/openwrt/voice-router.init` |

#### 预研 Web 架构（当前演示）

```
浏览器（localhost）                ESP32-S3（INMP441）
  ├─ 文本框 / 下拉 ──→ NLU          └─ 持续 PCM WebSocket
  └─ 按住说话（可选）──→ ASR→NLU              │
         │                                    ▼
         └──────────────→ Mac Web 服务 ← 音量唤醒 → 单次采集 → ASR → NLU
                              │
                              ├─ 路由器意图 → mock ubus（展示 NLU）
                              └─ 风扇意图   → WebSocket fan 指令 → ESP32 GPIO
```

**演示双轨**（详见 [周三演示脚本.md](docs/周三演示脚本.md)）：

| 轨道 | 输入 | 展示重点 |
|------|------|----------|
| A · 路由器 | 文本框 / 浏览器麦（仅 localhost） | NLU 意图分类；Mac 上 mock 执行 |
| B · 风扇 | ESP32 麦克风全链路 | 唤醒 → ASR → NLU → 风扇转停 |

ESP32 链路采用 **方案 1**：服务端 `VolumeWakeDetector` 音量触发 → 单次 utterance 采集 → ASR → NLU（`wake_policy.py` / `ws_audio.py`）。**不再**以 KWS 模型作为 ESP32 主唤醒路径。

### 2.1 分阶段内存（128MB 路由器，优化后）

| 阶段 | 加载组件 | 内存占用 | 备注 |
|------|---------|---------|------|
| 待机 | 系统 + KWS + NLU(INT8) + Buf | **~77MB** | 无 ASR 常驻（引擎 ~17MB） |
| 唤醒峰值（Python ASR） | + ASR 子进程（KWS 已卸载） | **~94MB** | 引擎 ~34MB |
| 唤醒峰值（C++ ASR） | + 原生 worker | **~70MB** | 无 Python 解释器开销 |
| 识别后 | ASR 进程退出 | **~77MB** | 自动回落 |

| 项目 | 磁盘/运行时 |
|------|------------|
| 系统基础（OpenWRT + Python） | ~60MB |
| ASR（zipformer zh 14M mobile） | **24MB** 文件 / 子进程 ~25MB |
| KWS（sherpa-onnx 3.3M） | **5MB** 文件 / ~8MB 运行时 |
| NLU INT8 | **~3MB** 文件 / ~4MB 运行时 |
| 音频缓冲 | ~5MB（含解码工作区；原始 2s PCM 仅 ~0.06MB） |

> **重要**：必须使用 `download_models.sh` 下载的 **zh 14M mobile** 模型（~25MB），勿使用 bilingual 大模型（~189MB）。Web 服务默认 `prefer_int8_nlu`，已提供 `models/nlu/intent_model.int8.onnx`（~2.8MB）。

### 2.1.1 与控制台「全机内存（路由器）」对照

控制台 **不是 Mac 进程 RSS**，也 **不是启动时写死的 24MB**；由 `RouterMemoryTracker` **每 2 秒**刷新：

| 环境 | 数据来源 | 行为 |
|------|---------|------|
| **Mac 预研 Web** | `router_sim` 状态机 | 待机 **77MB**（60 系统 + KWS8 + NLU4 + Buf5）↔ 识别峰值 **94MB**（ASR 时 KWS 卸载） |
| **OpenWrt 真机** | `live_rss` | `/proc/meminfo` 全机 used + voice-routerd 进程 RSS |
| **OpenWrt Web+daemon** | `daemon_snapshot` | 读 `/tmp/voice-router-memory.json`（daemon 每 2s 写入） |

ASR 开始时 `enter_router_asr()`，结束后 `exit_router_asr()`；说一句话时进度条应在 **~60% ↔ ~73%** 之间跳动。

环境变量：`VOICE_ROUTER_MEMORY_MODE=router_sim|live_rss|daemon_snapshot`（默认 Mac=`router_sim`，真机=`live_rss`）。

实现链：`config.estimate_engine_memory` → `web/router_memory.py` → `monitor._sample()` → `/api/monitor`。

### 2.2 关键取舍

| 决策 | 原因 | 节省内存 |
|------|------|---------|
| ❌ 放弃实时TTS → 预录制音频拼接 | TTS模型 >30MB | ~30MB |
| ✅ 量产保留 KWS 唤醒词 | 路由器 USB 麦体验优于纯音量触发 | — |
| ⚠️ ESP32 预研改用音量唤醒（方案1） | INMP441 远场 + 无 KWS 算力；演示优先稳定性 | ESP32 Flash 零模型 |
| ✅ 字符级 CNN+LSTM | 比 Transformer/BERT 小一个量级 | — |

## 三、技术选型

### 3.1 ASR：sherpa-onnx Zipformer（25MB）

| 方案 | 磁盘 | 运行时工作区 | 中文 | MIPS兼容 | 结论 |
|------|------|-------------|------|----------|------|
| sherpa-onnx Zipformer | ~24MB | **~25MB**（子进程峰值） | ⭐⭐⭐⭐ | ✅ ONNX | **选中** |
| Paraformer | 50-200MB | >50MB | ⭐⭐⭐⭐⭐ | ❌ FunASR生态 | 太重 |
| Vosk small | 42MB | ~40MB | ⭐⭐⭐ | ⚠️ 需编译 | 内存大 |
| Whisper tiny | 78MB | ~300MB | ⭐⭐⭐⭐ | ❌ 太大 | 不可行 |

**预研注意**：ESP32 麦 ASR 误识别率高（如「关闭风扇」→「封善」），风扇链路靠 `_esp32_mic_fan_override` + `strip_wake_prefix` 兜底；路由器语音在 ESP32 上**刻意收紧**（`esp32_mic=True` 时低置信度拒猜）。

### 3.2 NLU：CNN+LSTM（11MB fp32 / 3MB INT8）

| 方案 | 模型大小 | 意图分类 | 槽位提取 | 结论 |
|------|---------|---------|---------|------|
| **CNN+LSTM** | 11MB (fp32) / **2.8MB (INT8)** | 16类，99.8% | BIO序列标注，37标签 | **选中** |
| FastText | 几百KB | ✅ | ❌ 靠规则引擎 | 无槽位能力 |
| Transformer tiny | 10MB | ⭐⭐⭐⭐⭐ | ✅ | 内存不够 |
| 纯规则引擎 | 0MB | ⭐⭐⭐ | ❌ | 兜底用 |

服务端另维护 **47 条路由器朗读 ASR 纠错表**（`service.py` `_repair_voice_command`，源自 `asr_debug/router_voice_readthrough.template.csv`），用于浏览器麦/文本链路，**不写入 ESP32**。

### 3.3 语音反馈：预录制音频拼接（0MB运行时）

录制 20-30 条常用回复，根据 NLU 结果选择播放。

### 3.4 同行方案对比：Paraformer + FastText

| 层级 | 本方案 | Paraformer + FastText |
|------|--------|----------------------|
| ASR | Zipformer 25MB（MIPS 可交叉编译） | Paraformer 50-200MB（MIPS 不兼容） |
| NLU 意图 | CNN+LSTM，16类 99.8% | FastText，仅分类 |

#### 为什么 Paraformer + FastText 方案不具备参考价值

以下从工程落地的客观约束逐层分析，这些判断基于物理限制和架构规范，而非主观偏好。

**一、硬件兼容性硬伤 —— 无法在目标芯片上运行**

本方案 Zipformer 裁剪至 25MB，且支持 MIPS 交叉编译，是真正面向低成本硬件的生存逻辑。对方 Paraformer 体积在 50-200MB，且 **MIPS 不兼容**。这意味着对方所谓的"跑通"，大概率是在 PC 或资源极其宽裕的 ARM 验证板上完成的。在一个目标定为 MIPS 架构的项目里，拿一个无法在 MIPS 上编译运行的方案作为进度标杆，这在架构评审阶段就应被直接否决。

**二、部署栈复杂度失控 —— 内存碎片与调度冲突**

嵌入式环境对系统开销极其敏感。本方案是单一 ONNX Runtime，部署链路干净。对方方案需要两套推理栈加一套规则引擎。在受限的内存环境下，每增加一套运行环境，内存碎片和系统底层调度冲突的概率呈指数级上升。这种架构在长期运行中几乎必然导致系统崩溃。

**三、维护成本与容错率的错判**

路由器场景的实体提取（设备名、带宽值、安全策略等）是动态变化的。对方采用 FastText 仅做分类，后续强依赖正则和关键词。这种方案在早期跑固定 Demo 时显得很快，但只要业务场景开始泛化，规则引擎就会变成一个永远填不完的逻辑黑洞。本方案 CNN+LSTM 配合 BIO 序列标注一步到位，并且做了错误注入训练——这是典型的将系统复杂度消化在训练阶段，从而保障端侧推理的极简与鲁棒。

> **定性结论：对方做的是一个无视物理约束、只为尽快发声的演示原型。本方案做的是一个符合目标架构、具备长周期维护潜力的工业级系统。** 客观的技术指标和物理限制是任何管理话术都无法掩盖的。

## 五、硬件连接

### 5.1 当前方案：ESP32 边缘节点（预研验证中）

```
Mac / 路由器 (语音引擎)                    ESP32-S3（仅采集 + 执行）
      │                                        ├── INMP441 麦克风（I2S 16kHz）
      │  WiFi WebSocket /ws/audio?role=esp32   ├── GPIO/PWM → TB6612 → 风扇
      └────────────────────────────────────────├── 四位数码管 + 0.96" OLED
                                               ├── NTC 温度（GPIO2 ADC）
                                               └── GPIO1 按键 → button_wake
```

#### ESP32 存了什么 / 没存什么

| 位置 | 内容 |
|------|------|
| **Flash（编译进固件）** | `config.h`：WiFi、HUB 地址、引脚、采样率；**无** NVS/Preferences/EEPROM |
| **RAM（断电丢失）** | 风扇状态、录音 UI 计时、VU、温度采样、WebSocket 会话 |
| **不在 ESP32** | ASR/NLU/KWS 模型、命令历史、路由器状态、温度持久化 |

温度由 ESP32 **周期性上报**，Mac 侧写入 `data/esp32_state.json` 供控制台恢复显示。风扇逻辑状态以 **Mac `DeviceManager` 为准**；ESP32 重连时服务端 `sync_device_state` 下发当前档位。

#### 方案 1 音频链路

1. 连接后服务端发 `start_kws` → ESP32 **持续推 PCM**（`g_kws_listening`，名称沿用旧协议）
2. Mac `VolumeWakeDetector` 检测音量突增 → `wake_detected` → **单次采集**（最长 5s，静音 0.8s 截断）
3. ASR → NLU（`esp32_mic=True`）→ `fan` 事件 → ESP32 执行并 `device_state` ACK
4. 冷却 **3s**（`VOICE_ROUTER_WAKE_COOLDOWN_SEC`）防连触

可调环境变量：`VOICE_ROUTER_VOLUME_WAKE_PEAK/RMS`、`VOICE_ROUTER_COLLECT_SEC`、`VOICE_ROUTER_SILENCE_SEC`。

### 5.2 目标方案：路由器直连（生产部署）

```
路由器 (OpenWRT)
  ├── USB → USB-I2S音频模块 → INMP441 麦克风 + MAX98357A DAC → 喇叭
  ├── GPIO → 继电器模块
  └── WiFi → ESP32等扩展设备（可选，仅作家居执行端）
```

> ESP32 中继适合预研阶段快速验证风扇/显示；**路由器语音本体**推荐 USB-I2S 直连 + Daemon KWS，减少延迟和故障点。

### 5.3 预研指令采集（asr_debug）

演示或调试时可开启 WAV 落盘，供 NLU 误识别再训（**不训练 ASR**）：

```bash
VOICE_ROUTER_SAVE_ASR_WAV=1 VOICE_ROUTER_ASR_DEBUG_DIR=./asr_debug \
  python3 -m voice_router_lite web
python3 tools/collect_asr_samples.py --dir ./asr_debug
```

可调采集窗：`VOICE_ROUTER_SKIP_SEC`、`VOICE_ROUTER_MIN_COMMAND_SEC`。

> ESP32 方案 1 默认**不需要** `VOICE_ROUTER_ENERGY_WAKE=1`（该变量用于浏览器/旧 KWS 能量兜底，ESP32 主路径已改为音量策略）。

### 5.4 OpenWrt 双进程（Web + daemon）

| 服务 | init 脚本 | 说明 |
|------|-----------|------|
| `voice-routerd` | `deploy/openwrt/voice-routerd.init` | KWS/ASR/NLU/TTS，`ENERGY_WAKE=0` |
| `voice-router-web` | `deploy/openwrt/voice-router-web.init` | FastAPI `:28080`，无 ALSA |

守护进程 RSS 阶段日志：`RSS [daemon_start|after_initialize|after_kws_listen|after_shutdown]`。

内存硬线（128MB）：待机 ≤75MB，唤醒峰值 ≤88MB，ASR 退出后 ≤76MB（待实机/QEMU 填入实测）。

## 七、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 内存不足 | 高 | 严重 | NLU INT8（已导出）；极端情况纯规则引擎兜底 |
| MIPS兼容性 | 中 | 严重 | 提前 QEMU 模拟 MIPS 验证；备选 256MB 双核路由器 |
| ESP32 麦 ASR 差 | 高 | 中等 | 演示风扇用方案1 + 关键词 override；路由器走文本/浏览器麦 |
| ASR准确率不高 | 中 | 中等 | NLU 训练注入 30% ASR 错误变体；运行时 47 条纠错表 |
| NLU理解错误 | 中 | 中等 | 置信度 <0.5 拒猜；ESP32 路由器意图额外收紧 |
| 路由器性能差 | 高 | 中等 | VAD 静音检测；cgroups CPU 配额 |
| 浏览器麦不可用 | 中 | 低 | 仅 `http://localhost:28080` + Chrome/Safari；演示主路径用文本框 |
