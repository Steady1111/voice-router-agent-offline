## 0.1 技术栈总览

### 语言与运行时

| 层级 | 语言 | 运行时 / 框架 | 代码位置 |
|------|------|---------------|----------|
| **语音服务端** | **Python 3.8+** | 标准 CPython | `voice_router_lite/` |
| **Web 后端** | Python | FastAPI + Uvicorn | `voice_router_lite/web/` |
| **Web 前端** | **HTML / CSS / JavaScript (ES Module)** | 浏览器原生，无 React/Vue | `voice_router_lite/web/static/` |
| **设备固件** | **C++ (Arduino)** | ESP-IDF / Arduino-ESP32 | `firmware/src/` |
| **NLU 训练** | Python | **PyTorch** → 导出 ONNX | `voice_router_lite/nlu/train_nlu.py` |
| **量产 OS** | Shell + JSON 配置 | **OpenWrt** + procd | `deploy/openwrt/` |

### AI 与语音引擎（全部离线，ONNX 推理）

| 能力 | 引擎 | 模型 | 推理库 | 体积（约） |
|------|------|------|--------|------------|
| 唤醒 KWS | sherpa-onnx Transducer | `models/kws/*.onnx` | sherpa-onnx | ~5MB |
| 语音识别 ASR | sherpa-onnx Zipformer | `models/asr/*.onnx` | sherpa-onnx | ~25MB |
| 指令理解 NLU | 自研 CNN+LSTM | `models/nlu/intent_model.onnx`（可 INT8） | **ONNX Runtime** | 11MB / 3MB |
| 语音合成 TTS | 预录 WAV 拼接 | `audio_clips/` | 无神经网络 | 磁盘 <5MB |
| VAD / 降噪 | WebRTC VAD + 频谱门 | 无模型 | webrtcvad / scipy | 可忽略 |

**刻意不采用：** LLM、Whisper、Paraformer、云端 API。

| 类别 | 库 |

| 测试 | pytest |
| 训练（仅开发机） | torch（未写入运行时依赖，训练时手动安装） |

| 链路 | 协议 | 数据格式 |
|------|------|----------|
| 浏览器 ↔ 服务端 | HTTP + **WebSocket** | JSON 事件 + 可选 PCM |

| 服务端 ↔ OpenWrt | **ubus** CLI（量产） | JSON |
| 浏览器 TTS 兜底 | Web Speech API | speechSynthesis |

## 0.7 端到端数据流（语音控风扇 · 预研）

```
用户说话
  → INMP441 → ESP32 I2S → WebSocket PCM
  → Python ws_audio：KWS（或能量唤醒 A 线）
  → 采集一段音频 → ASR（Zipformer）→ 文本
  → NLU（CNN+LSTM）+ 规则兜底 → intent + slots
  → DeviceManager → ESP32Bridge → JSON fan 命令
  → ESP32 PWM 驱动风扇 + RGB/数码管反馈
  → WebSocket 广播 → 浏览器显示 transcript/reply
  → 浏览器 speechSynthesis 播报（或 TTS WAV / 蜂鸣）
```

量产路径：麦克风改 **ALSA 直连**，唤醒仅 **KWS B 线**，路由器意图走 **ubus**，Web 与 daemon **分进程**。

## 硬件接线记录

### INMP441 麦克风（2026-06-15）

> 适用于 ESP32-S3 预研阶段。路由器端需使用 USB-I2S 音频模块。

| INMP441 引脚 | ESP32-S3 引脚 | 说明 |
|-------------|--------------|------|
| VDD | 3V3 | 供电 |
| GND | GND | 地 |
| SCK | GPIO 4 | 位时钟 BCLK |
| WS | GPIO 5 | 帧时钟 LRCLK |
| SD | GPIO 6 | 数据输出 DIN |
| L/R | GND | 选左声道（接 GND，不可接 VDD） |

**路由器端替代方案：**
```
路由器 USB ──→ CP2104 USB-I2S 音频模块
                  └── INMP441 麦克风 (I2S输入)
```

### TB6612 电机驱动 + 130 风扇（2026-06-15，2026-06-22 更新供电方案）

| TB6612 引脚 | 接法 | 说明 |
|------------|------|------|
| VM | **独立 USB 充电头 5V** | 🔄 电机独立供电（2026-06-22 改），避免与 ESP32 共用 USB 5V 导致电压跌落复位 |
| VCC | ESP32 3V3 | 逻辑供电 |
| GND（两个都接） | ESP32 GND + 独立电源 GND | ⚠️ 必须共地，否则 TB6612 收不到控制信号 |
| STBY | ESP32 3V3 | ⚠️ 必须接，不然芯片不工作 |
| PWMA | GPIO 9 | PWM 调速 |
| AIN1 | GPIO 8 | 控制信号（HIGH=转，LOW=停） |
| AIN2 | GND | 单向转动 |
| AO1 | 电机正极 | 驱动输出 |
| AO2 | 电机负极 | 驱动输出 |

> **供电问题根因**（2026-06-22 定位）：
> 电机大电流 + ESP32 共用同一路 5V → 电压跌落 → ESP32 掉电复位
> **解决方案**：VMOT 改为独立 USB 充电头供电，两路 GND 必须接在一起（共地）。

**路由器端替代方案：**
```
路由器 GPIO ──→ 继电器模块 ──→ 风扇/其他设备
或
路由器 USB ──→ USB-TTL ──→ MCU ──→ 设备控制
```

### 四位数码管 0.56" 4位共阴（2026-06-16）

> GPIO 直驱方案，无驱动芯片，动态扫描（100Hz，2500μs/位）。段引脚各串 470Ω 限流电阻。

| 数码管引脚 | ESP32-S3 引脚 | 说明 |
|-----------|--------------|------|
| 12 (DIG1) | GPIO 18 | 千位选通（共阴：LOW=选中） |
| 11 (A) | GPIO 10 | 段 A，串 470Ω |
| 10 (F) | GPIO 15 | 段 F，串 470Ω |
| 9 (DIG2) | GPIO 19 | 百位选通 |
| 8 (DIG3) | GPIO 20 | 十位选通 |
| 7 (B) | GPIO 11 | 段 B，串 470Ω |
| 6 (DIG4) | GPIO 21 | 个位选通 |
| 5 (G) | GPIO 16 | 段 G，串 470Ω |
| 4 (C) | GPIO 12 | 段 C，串 470Ω |
| 3 (DP) | GPIO 17 | 小数点，串 470Ω |
| 2 (D) | GPIO 13 | 段 D，串 470Ω |
| 1 (E) | GPIO 14 | 段 E，串 470Ω |

> 显示规则：**录音中 → 显示秒数（如 `0012`）；风扇开 → 显示转速 PWM 值（如 `0255`）；空闲 → 显示 `----`**。

- 路由器通常无 GPIO，需通过 USB-TTL 连接外部 MCU 驱动显示

## 常见问题速查

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 设备不识别 | USB 线或驱动 | 重新插拔；按住 BOOT 再插 USB |
| 烧录失败 `device disconnected` | 串口被占用 | 关闭 `pio device monitor` |
| WiFi `NO_AP_FOUND` | SSID 不匹配 | 检查热点名称；开启兼容模式 |
| 烧录速度不稳定 | 速度过高 | 降到 115200 bps |
| RGB 红灯（WebSocket 不通） | 防火墙/IP 错误 | 关防火墙；检查 HUB_HOST |
| 风扇转一下就停 | 电压跌落 | **电机独立供电**（见 TB6612 接线） |
| 数码管闪烁 | 扫描间隙过大 | 恢复 200ms 双层循环 + 10ms burst |

# 第二部分：硬件层技术选型

> 本章节从参考项目同步，记录硬件选型的利弊分析。

## 主控芯片：ESP32-S3 vs 其他方案

| 方案 | 选型理由 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| **ESP32-S3（预研用）** | 自带 WiFi/BT，双核 240MHz，支持 PSRAM | 集成度高，开发资源丰富 | GPIO 数量有限 | 物联网项目、语音采集边缘节点 |
| **路由器 SoC（最终目标）** | 百元路由器内置 | 成本低，直接部署 | 需 USB-I2S 扩展音频接口 | 最终部署目标 |

**决策**：预研阶段用 ESP32-S3 验证音频采集和设备控制逻辑，最终部署到路由器。

## 麦克风：INMP441（I2S）vs 其他方案

| 方案 | 选型理由 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| **INMP441（已选）** | I2S 数字输出，无需 ADC | 音质好，抗干扰强 | 需要 3 根 GPIO | 高质量音频采集 |
| **USB 麦克风（路由器推荐）** | 即插即用 | 无需驱动 | 成本高 | 路由器端音频采集 |

**决策**：预研阶段用 INMP441，路由器端用 USB 麦克风或 USB-I2S 模块。

## 电机驱动：TB6612 vs 其他方案

| 方案 | 选型理由 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| **TB6612（已选）** | 套件自带，双通道 | 驱动能力强（1.2A/通道） | 需要外接电源（VM） | 直流电机、风扇 |
| **继电器模块（路由器推荐）** | GPIO 直接控制 | 成本低，隔离好 | 只能开关，不能调速 | 简单开关控制 |

**决策**：预研阶段用 TB6612（支持 PWM 调速），路由器端用继电器模块（简单开关）。

## 2026-06-23 — 离线语音方案确立与代码实现

### 方案设计阶段

**背景**：原 `voice-router-agent` 项目基于 ASR+LLM（Whisper + Ollama + Piper TTS），需要大模型推理，无法部署在 128MB MIPS 路由器上。需要重新设计一套纯离线、轻量化的语音方案。

**核心约束**：
- 目标设备：128MB MIPS 百元路由器，实际可用内存 ~50MB
- 所有功能必须在单一设备完成，无协同设备
- 不能使用大模型，只能用传统深度学习模型
- 需要支持：语音唤醒、ASR、NLU、TTS、设备控制

**架构演化**：
```
初版方案 → ESP32协同（唤醒词+TTS） + 路由器（ASR+NLU）
用户明确 → 纯路由器独立运行，无协同设备
最终方案 → 路由器端 ASR(sherpa-onnx 25MB) + NLU(CNN+LSTM 2MB) + TTS(预录制0MB)
```

**关键技术决策**：

| 决策点 | 选项 | 选择 | 理由 |
|--------|------|------|------|
| ASR | sherpa-onnx vs Vosk vs Whisper | **sherpa-onnx Zipformer** | 25MB 唯一在50MB内可运行的优质中文ASR |
| NLU | CNN+LSTM vs Transformer vs 规则引擎 | **CNN+LSTM + 规则兜底** | 2MB平衡体积和准确率，ONNX加载失败自动回退规则 |
| TTS | Piper TTS vs 预录制拼接 | **预录制音频拼接** | 零运行时内存，Piper需要20MB |
| 唤醒词 | sherpa-onnx KWS vs 按键触发 | **能量唤醒(调试)/sherpa-onnx KWS(部署)** | 预研阶段用能量检测简化，部署时加载完整模型 |
| 降噪 | 频谱门 vs WebRTC vs RNNoise | **频谱门** | CPU轻量，无额外模型依赖 |

**内存预算验证**：
```
系统基础:  57MB (内核+OpenWRT+Python)
ASR:       30MB (25MB模型+5MB运行时)
NLU:        5MB (2MB模型+3MB运行时)
音频缓冲:   5MB
WebSocket:  3MB
─────────────
总计:     100MB (128MB内 ✅)
```

**模型训练方案确立**：
- ❌ ASR 从零训练不可行（需1000+小时数据，成本¥150万+）
- ✅ 唤醒词可微调（100条正样本，基于sherpa-onnx预训练模型）
- ✅ NLU可从零训练（500-1000条标注数据，CNN+LSTM）
- TTS不需要训练，用预录制音频拼接

## 2026-06-25 — 监控面板重构 & 同行方案对比优化

### 性能监控面板重构：从 Mac 指标到路由器引擎估算

**问题**：原 `monitor.py` 使用 `psutil.Process()` 直接读取开发机（Mac）上 Python 进程的 RSS 内存和 CPU 占用，这些数据不反映路由器上离线引擎的真实资源消耗——Mac 多核 x86 大内存和 MIPS 单核 128MB 的 CPU/内存画像完全不同。

**修改文件**：

| 文件 | 修改内容 |
|------|---------|
| `voice_router_lite/web/monitor.py` | 移除 `psutil` 依赖；CPU 改为基于实际推理耗时估算；内存改为仅追踪引擎核心模块 |
| `voice_router_lite/pipeline.py` | `_log_memory_estimate()` 中调用 `get_monitor().update_engine_memory()` 同步引擎内存 |
| `voice_router_lite/web/ws_audio.py` | KWS/ASR/NLU 推理前后计时，调用 `record_inference_time()` 记录耗时 |

**核心设计变更**：

1. **CPU 监控**：不再依赖 `psutil.Process().cpu_percent()`，改为基于推理耗时估算

   ```
   CPU% = (采样窗口内 KWS+ASR+NLU 推理总耗时 / 采样窗口时长) × 100
   ```
   这反映的是"如果路由器单核跑这些推理任务，会占用多少 CPU"，而非 Mac 的 CPU 占用。CPU 上限钳制在 100%。

2. **内存监控**：不再读取整个进程 RSS，改为**仅追踪离线引擎核心模块**的内存占用：
   - KWS 模型 + ASR 模型 + NLU 模型 + 音频缓冲区
   - 不包含 Python 解释器、系统库、Web 框架等与路由器部署无关的开销
   - Pipeline 初始化完成后通过 `update_engine_memory()` 写入估算值

3. **新增公开 API**：
   - `update_engine_memory(ram_mb)` — 更新引擎内存估算
   - `record_inference_time(stage, elapsed_ms)` — 记录单次推理耗时（stage: "kws"/"asr"/"nlu"）

4. **推理耗时采集覆盖**：
   - KWS：每帧 `kws_engine.detect()` 前后计时（ESP32 链路）
   - ASR：`asr.transcribe()` 前后计时（ESP32 链路 + 浏览器链路）
   - NLU：`command_service.handle_text()` 前后计时（ESP32 链路 + 浏览器链路）

**修改后的 snapshot 返回值**：
- `current_ram_mb` / `peak_ram_mb` → 引擎核心模块内存（非进程 RSS）
- `cpu_percent` → 基于推理耗时估算的 CPU 占用率
- `host_info.note` → 新增字段，标注"CPU/内存均基于离线引擎核心模块估算，非开发机实际指标"

### 同行方案对比文档优化

**文件**：`离线语音方案-路由器部署.md` 第 3.4 节

在原有对比表格基础上，新增三个维度的工程论证，说明 Paraformer + FastText 方案不具备参考价值的根本原因：

1. **硬件兼容性硬伤**：Paraformer 50-200MB 且 MIPS 不兼容，对方"跑通"大概率是 PC 或 ARM 验证板，无法在目标 MIPS 芯片上编译运行——架构评审阶段即应否决。

2. **部署栈复杂度失控**：两套推理栈 + 规则引擎在受限内存下，内存碎片和调度冲突概率指数级上升，长期运行必然崩溃；本方案单一 ONNX Runtime 部署链路干净。

3. **维护成本与容错率的错判**：FastText 仅分类 + 正则/关键词规则引擎在动态场景下是逻辑黑洞；本方案 CNN+LSTM + BIO 序列标注一步到位，错误注入训练将复杂度消化在训练阶段，保障端侧推理极简鲁棒。

**定性结论**：对方是演示原型，本方案是工业级系统。

### 3. DS18B20 温度传感器故障排查

**症状**：
- 串口 `DEBUG: temp=nanC ok=0`，传感器未检测到
- 启动日志 `Temp: DS18B20 on GPIO X, first=-999.0C`
- OLED 无温度显示（`g_temp_ok = false` 跳过了绘制）
- 前端 `temperature_c: null`（遥测因 `g_temp_ok` 为 false 而未发送）

**排查过程**：

| 步骤 | 结论 |
|------|------|
| 检查 `TEMP_SENSOR_ENABLE` 宏 | 已设置为 1 ✅ |
| 检查 OneWire 引脚配置 | 原 GPIO 2，后改为 GPIO 38 |
| 检查供电电压 | **传感器曾接 5V**，ESP32-S3 GPIO 仅承受 3.3V ⚠️ |
| 检查上拉电阻 | 使用 1kΩ（手册推荐 4.7kΩ，1kΩ 在安全范围内可用） |
| 换引脚重试 | GPIO 2 → GPIO 38，重新烧录，问题依旧 |

**推测根因**：DS18B20 之前 VCC 接 5V 时，DQ 数据脚输出 5V 电平灌入 GPIO 2，可能已损坏 GPIO 2 和/或传感器本身。换到 GPIO 38 后传感器仍未被 OneWire 总线检测到，传感器硬件本身可能已损坏。

**待验证**：更换新的 DS18B20 传感器，使用 GPIO 38，VCC 务必接 3V3，DQ 上拉 1kΩ~4.7kΩ 到 3V3。

### 4. 重要硬件注意事项

| 项目 | 正确做法 | 错误做法 |
|------|---------|---------|
| DS18B20 供电 | **3V3**（ESP32 GPIO 安全） | 5V（会烧 GPIO） |
| 上拉电阻 | DQ → 1kΩ~4.7kΩ → 3V3 | 无上拉或拉到 5V |
| HUB_HOST | 保持与 Mac 当前 IP 一致 | 硬编码过期 IP |
